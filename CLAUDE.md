# fluxchat — Claude Code Context

## What is this
A cross-platform Matrix chat client written in Rust (the desktop app; `android/` is a Kotlin agent companion). IRC-inspired UI, tmux-style panes, and first-class controls for AI agents run over Matrix (Hermes Agent today; see `agents.rs`). Positioned as the client for people who talk to humans *and* run AI agents (README "Why fluxchat" / "Built for running AI agents" / "Where it's going" roadmap — keep the roadmap honest: only built things go in the feature lists). Uses matrix-rust-sdk + matrix-sdk-ui for the Matrix protocol and Timeline API.

- **Agent list sync** (core `agent_list.rs`): `Prefs::agents` / `agent_harness` / `not_agents` mirror global account data `org.fluxchat.agents` (`{"agents":[{"user_id","harness"}],"not_agents":[…]}`), shared with the Android app. `load_agent_list` after the initial room list (reads it and registers a handler for live changes → `AgentListSynced`); the account's list wins (`apply_agent_list`), none saved → ours is uploaded; `SetAgent` / `SetAgentHarness` / `NotAnAgent` call `save_agent_list` (only once loaded, `agent_list_loaded`)
- **Cargo workspace** with two crates:
  - `crates/core/` — pure business logic, no UI deps. Matrix operations, Timeline management, message conversion, GIF search (Giphy API).
  - `crates/app/` — Iced desktop frontend (native GPU-rendered via wgpu, Elm architecture)
- **Timeline API**: `matrix-sdk-ui` Timeline per room handles loading, pagination, live updates, local echo, edits, reactions, redactions. Thread timelines via `TimelineFocus::Thread`.
- **Storage:** rusqlite for app data (sessions, media cache, settings, emoji frequency), matrix-sdk's built-in SQLite for crypto/sync/event cache
- **Sync:** Pure sliding sync via `SyncService` from matrix-sdk-ui. Room list updates via reactive `RoomListService` stream watcher. Typing + verification handlers registered directly on client. No legacy `/sync` loop.
- **State:** Plain `FluxChat` struct with all fields as owned data. Elm architecture: `Message` enum → `update()` returns `Task<Message>` → `view()` renders UI. No signals, no JS interop.

## Key Design Decisions
- Pure Rust (desktop) — no JavaScript, TypeScript, or Node.js. Fully native GPU-rendered via wgpu. The Android companion is Kotlin by choice (prebuilt SDK bindings; iced's Android/IME support isn't there)
- IRC-inspired: right-aligned nicks with vertical separator, colored nicks, monospace fonts throughout, status bar with mode badges (@/+), room header bar with space/room name
- Timeline API for all message operations (not manual /messages API)
- Modular slash command system in `commands.rs` — add new commands by adding entries to `all_commands()`
- **Panes & windows (tmux-style, `panes.rs`)**: each `Window` is an iced `pane_grid` of `PaneSlot { key }` (room, thread, or empty); `windows`/`active_window`. The focused pane of the active window *is* the main view (`selected_room_id`; `SelectRoom` → `focus_key_in_pane`) and renders the full `view_content()`; other panes render `view_pane_body` (non-virtualized, last `SIDE_PANE_ROWS`, own composer in `pane_inputs`, `PaneSend`); its list is `anchor_bottom` (call it *after* `.direction(..)`, which replaces the scrollbar and resets the anchor), so offsets count from the bottom — scroll it with `pane_snap_bottom`, never `snap_to_end` (that goes to the top), and the body is wrapped in `isolated::Isolated` (own tree tag) so it never inherits the full view's widget state — iced matches state by tree position, and the main list's "at bottom" offset read upside down there). Title bars (drag to rearrange, split/zoom/close) when a window has >1 pane; iced lays the title out at full width and hides it if it doesn't fit beside the controls, so titles are capped at `pane_widths()` (grid regions from the window size minus surrounding panels) − `TITLE_BAR_RESERVED` and clipped. The focused pane's title is the room header itself (`view_room_header(key, Some(width))`, fixed to that cap; `view_content` leaves its own header out when the grid has >1 pane); below `HEADER_FULL_ACTIONS_WIDTH` it keeps search/threads/members and the agent chip goes compact (icon + dot, text in the tooltip). The header's name/chip side is a `Fill` container laid out after the actions, so it's the part that clips. Pane focus: pane_grid's `on_click` fires on mouse *press*, but focusing swaps the pane's widget tree (compact body → full view), which would swallow the click — so `PaneClicked` only records `pending_pane_focus` and the left-release (`SidebarDragEnd`) commits it (`commit_pane_focus`, also focuses the composer); title-bar controls use the immediate `PaneFocus`. Splitting keeps focus on the current view (no palette); an empty pane in a split renders `view_empty_pane(pane)`, a room picker whose rows send `FillPane(pane, key)` (rooms open in any window are left out). `focus_key_in_pane` (from `SelectRoom`) puts a new room in the window's empty pane if there is one (so a sidebar pick after a split doesn't replace the room you were reading) and returns the view it replaced, which `SelectRoom` releases; `replace_focused` (Here / centre drops) writes the focused slot itself to bypass that. Zoom: `Window::unzoom_for` on every focus change, `grid.restore()` before splitting or reusing another pane, lone panes can't zoom, persisted as `SavedWindow.zoomed`. A room that's gone (`LeaveRoom`, or vanished from the room list) → `forget_room_in_panes` closes its panes and its threads' panes in every window (empties a window's last pane) and re-syncs the main view. `panes::flow_tests` drive these flows through the real `update()` with a temp DB and no client — add a test there for any pane/window behaviour change. `view_message(view_key, msg, ..)` takes the view it renders in — never read `selected_room_id` inside it; side panes wrap row messages with `panes::in_view`, which turns room-acting ones (react/reply/edit/delete/pin/menus) into `InView(key, msg)` (focus that pane, then run) and passes hover/selection/links through. Keys: Ctrl+B prefix (`PREFIX_ARMED` static, flipped synchronously in the global `listen_with` closure, so composers swallow the command key via `tmux_binding`; commands read from `modified_key` because iced's `key` ignores Shift — `%` would arrive as `5`; key repeat ignored) then `%` `"` `x` `z` `o` arrows/hjkl `c` `n` `p` 0–9 `&` `?`. Opening views: `open_at(key, Placement)` (`OpenAt`; `OpenThread` = thread key + `Auto`). A plain open (`Auto`/`Follow`) of something already open in *any* window focuses that copy (`locate`, also used by `focus_key_in_pane`, so `SelectRoom` of a room open in another window switches windows — never a second copy); an explicit placement (`Right`/`Below`/`Here`/`NewWindow`) opens a second view where asked even when it's already on screen (deliberate: the menu said so). Both room and thread context menus (`ContextMenu::Room`/`Thread`) always offer Open to the right / below / in this pane / in new window, plus Go to room/thread when already on screen. List rows go through `list_entry_area` (right-click menu, middle-click → `OpenAt(.., Right)`) and click with `ListClick(key, plain)` (Cmd/Ctrl held — `view::open_modifier_held()`, `MODIFIERS` static from `ModifiersChanged` — → Right; a click right after a drag is ignored). Drag & drop (`dnd.rs`): `dnd::source` on room-list / thread rows (not summary rows inside panes — a press there is a pane click), `dnd::target` on each pane; state in a static (no Message per cursor move); the pressed row itself decides when its press becomes a drag, comparing positions in its own coordinates (`moved_enough`, `cursor.land()`) — inside the scrolled room list they're offset by the scroll, so comparing with window coordinates made every click a "drag" and rows stopped responding; the target shades the zone (edges split that side, middle replaces) and sends `DropOnPane` → `drop_on_pane`; `SidebarDragEnd` calls `dnd::released()`. Rooms in unfocused panes: softer sidebar highlight (`visible`), and `room_visible` (any pane of the active window, incl. its threads) suppresses desktop notifications. Esc with nothing else to close in a thread pane → `escape_to_room`. `Auto`/`Follow` → `show_beside(key, follow)` (split right; `OpenThread` is in `in_view`, so a click in an unfocused pane makes that pane the origin. A plain `Auto` thread NEVER replaces a pane — every thread gets its own pane; only `Follow` (agent thread-follows from `thread_to_follow`, so a stream of runs doesn't stack panes) reuses a same-room thread pane — `adjacent()` to the focused pane first, so the thread under/beside its room is the one swapped — or the focused pane when that is itself a same-room thread; replaced threads go through `release_view`). Layout of all windows persisted as JSON (`pane_layout`, `save_layout` on Tick via `layout_dirty`, `restore_layout` after the room list loads). Status bar shows `0:name*` window list. ## App Architecture (`crates/app/`)
- **Elm architecture:** `FluxChat` state struct → `Message` enum → `update(&mut self, msg) -> Task<Message>` → `view(&self) -> Element<Message>`
- **Files:** main.rs (entry), agents.rs (AI agent runs/commands/approvals/Runs dialog/watch window/multi-agent/suggestions), harness.rs (agent harness profiles), prompts.rs (prompt history + snippets), history.rs (run history + transcript export), budgets.rs (agent spend limits), compare.rs (ask all agents + compare dialog), run_search.rs (run transcripts + full-text search), diff.rs (unified diff parser), review.rs (diff review dialog), progress.rs (progress bar: animated, or filled to a fraction), dnd.rs (drag rows onto panes), timing.rs (opt-in slow update/view log), anim.rs (budgeted GIF/WebP frames), panes.rs (panes/windows), state.rs (FluxChat struct + enums), message.rs (Message/SyncEvent), update.rs (core state transitions), update_settings.rs (settings/profile/security), update_spaces.rs (space dialog), update_call.rs (call/RTC), view.rs (layout/room list/content), view_messages.rs (message rendering), view_modals.rs (modals), view_profile.rs (profile card), view_space.rs (space dialog), ui.rs (dialog kit), view_members.rs (member list + call widget), view_input.rs (input bar/autocomplete), html.rs (Matrix HTML→Spans), selectable_text.rs (selectable rich text widget), commands.rs (slash commands), theme.rs (colors)
- **HTML rendering:** `html5ever`-based parser with arena DOM converts Matrix HTML to `Vec<Span>` for `selectable_rich_text` widget. Message HTML is untrusted: markup nested past `MAX_PARSE_NESTING` isn't parsed (html5ever's scope checks are quadratic in depth), the recursive `walk` flattens past `MAX_HTML_DEPTH`, and text collectors are iterative — a 64 KB event can nest ~20 000 tags, which used to overflow the main thread's stack (crash for everyone viewing the room). Handles bold/italic/strike/code/links/mentions/blockquotes/lists (ul/ol). Bare URLs in text nodes (not in code/mentions) become links (`find_urls`: `http(s)://`, `www.`, `host.tld/path`) — agents send formatted bodies without `<a>` tags. Syntax highlighting via syntect. Markdown-style bullets in formatted bodies auto-converted to HTML lists.
- **Selectable text:** Custom `SelectableRichText` widget (`selectable_text.rs`) replaces Iced's built-in `rich_text` for message rendering. Uses cosmic-text's buffer (already underlying Iced's text engine) for hit-testing, mouse click/drag selection, and Ctrl+C/Cmd+C copy. Preserves all existing span styling (colors, backgrounds, links, underlines, strikethrough). Link clicks still work on click without drag. Ctrl+A selects all text in hovered widget. Copy (`extract_selection_text`) uses what the view rendered: every selectable widget goes through `FluxChat::selectable` (view_messages.rs), which records its text in `selection_texts` while a selection exists — the widget's (line, index) refer to the rendered paragraph, so mapping them onto `msg.body` (markdown, different line breaks, other parts) copied wrong text or nothing; rows never rendered fall back to the body
- **Modals:** `stack` + `opaque` + `mouse_area` overlay pattern. Modal enum dispatches to Settings/CreateRoom/Profile/Verification/Lightbox/Forward/DevTools.
- **Commands:** 48+ slash commands producing `CommandResult` (Messages/Rewrite/Help/Noop). Decoupled from UI — returns Message variants. Display name resolution for /kick, /ban, /op, /deop.
- **Subscriptions:** `time::every(5s)` Tick for invites/typing expiry + call presence (member presence and all-room call scan every 6th tick), `keyboard::listen()` for Alt+1-9 + Escape, window focus events for notification suppression. Room list updates via reactive `RoomListService` stream (debounced 300ms). Cursor movement is recorded in atomics (`view::cursor_position()`) and only emitted as `Message::CursorMoved` while dragging the sidebar — every Message rebuilds the view.
- **Async:** Room commands (join/leave/invite/kick/ban/topic), file upload, search, member loading all via `Task::perform()`.
- **Status:** Fully functional — login, rooms, messaging, reactions, emoji picker, search, threads, back-pagination, media, modals, settings all implemented.

## Important Patterns
- Elm architecture: all state changes go through `Message` enum → `update()` → returns `Task<Message>`
- `Task::perform()` for async operations, `Task::batch()` to combine multiple tasks
- One watcher task per room Timeline (`core::timeline::RoomTimelines`), created together with the Timeline and aborted when it is removed. It mirrors the SDK item list by applying `VectorDiff`s (only changed items re-converted), coalesces bursts, and sends the full ordered list through the `TimelineSink` → `SyncEvent::MessagesUpdated`, which replaces `messages_by_room[room]` outright. Nothing else writes room messages — no Tick re-read, no merge, no drift detection. `request_snapshot()` asks a watcher to re-send.
- Locally deleted messages are hidden via `pending_redactions` until the timeline reflects the redaction (or `RedactionFailed` restores them)
- Avatar resolution uses sync media cache lookup + background async batch resolve for uncached MXC URIs
- Message list is virtualized: `visible_rows()` → `virtual_window()` picks rows within viewport ± `VIRTUAL_OVERSCAN` using measured heights (`row_heights`, filled by the transparent `Measured` wrapper in `measured.rs`; unmeasured rows use `ESTIMATED_ROW_HEIGHT`), with spacers above/below. `virt_anchor` records the first visible row + its offset each render; `MessagesScrolled` (also fired on content-size changes) compensates any change in that row's position (rows getting measured, history prepended) via `scroll_to`. Back-pagination (`start_back_pagination`) only when the user scrolls *up* into the top `PAGINATE_TOP_ZONE` (or content doesn't fill the view), or wheels up while already at offset 0 (the scrollable emits nothing then: `set_timeline_at_top` records the bounds and the global listener sends `TimelineWheelUpAtTop` only for wheel-ups inside them) — never on content-size changes, which made each small page trigger the next forever in thread-heavy rooms. One page in flight; it ends in `PaginateSettled` (250 ms after the request, so the rows have landed); a page adding nothing visible continues at most `MAX_EMPTY_PAGES` times while still at the top; while the content doesn't fill the view (`messages_underfilled`), pages are `UNDERFILL_PAGE_EVENTS` (100) and `PaginateSettled` itself starts the next one, visible rows or not, up to `MAX_UNDERFILL_PAGES` per room open (the page's content-size event arrives while it's still in flight and is dropped) and a failed page retries via `PaginateRetry` after `PAGINATE_RETRY_DELAY`; `history_start` stops it at the room's start. `JumpToEvent` uses `row_top()`.
- Emoji picker: `emojis` crate for data, `EmojiPickerMode::Insert`/`React(event_id)` for two trigger modes, frequency tracked in `HashMap<String, u32>` persisted as JSON to SQLite, 400px right-aligned panel; `EMOJI_CATEGORIES` gives each of the 10 tabs (frequent + 9 `emojis::Group`s) a Lucide icon + tooltip, equal-width so they always fit; category heading above a 9-column grid
- `read_rooms` HashSet is session-only (not persisted) — SDK's `notification_count` is authoritative on startup
- `nick_color_index` lives in `theme.rs` for shared access
- Thread replies detected via SDK `MsgLikeContent::thread_root` (populated since SDK 0.18)

## Voice Calls (MatrixRTC + LiveKit)
- **Architecture:** MatrixRTC signaling (m.call.member state events) + LiveKit SFU for audio transport
- **Token flow:** `.well-known` → `org.matrix.msc4143.rtc_foci` → `livekit_service_url` → OpenID token exchange → `POST /sfu/get` for LiveKit JWT
- **Core modules:** `rtc.rs` (MatrixRTC signaling: join/leave, state events, JWT exchange), `rtc_audio.rs` (LiveKit connection, cpal audio capture/playback)
- **Audio capture:** cpal input device → mpsc channel → tokio task → `NativeAudioSource` → LiveKit publish. Channel bridges sync cpal callback to async LiveKit API.
- **Audio playback:** `NativeAudioStream` from remote tracks → tokio task → ring buffer → cpal output stream. Output stream leaked into tokio task, cleaned up when track ends.
- **Quit:** `exit_on_close_request: false`; `CloseRequested` flushes the layout and leaves an active call (3 s timeout) before `iced::exit()` — the membership event otherwise keeps us "in" the call for its 4 h expiry. macOS Cmd+Q / the Quit menu bypass `CloseRequested` (winit exits from `applicationWillTerminate`), so `update_call::CALL_ON_EXIT` mirrors `call_room_id` and an `atexit` hook (`register_exit_hook`) leaves the call from there, on its own thread with the runtime still alive. The layout is flushed on Tick, so at most 5 s of layout changes are lost that way.
- **Call lifecycle:** `CallJoin` → get JWT → `CallSession::connect()` → publish mic (muted by default) → event loop drains `RoomEvent` → `CallEvent` → bridged to `Message` variants. `CallLeave` → `watch::channel` signal → `session.disconnect()` → `leave_call()` state event.
- **Participant tracking:** LiveKit events are source of truth during connected calls. Tick handler only updates room indicators, not participants, when connected.
- **UI:** In-call panel (participant tiles + controls) above messages, PIP in member list when viewing other rooms. Phone icon in tab bar action buttons. Join banner for rooms with active calls.
- **State events:** `m.call.member` (MSC3401) sent with `room.send_state_event_raw()`. Custom event type `org.matrix.msc3401.call.member` with `memberships` array. Empty memberships = left call. Suppressed from timeline rendering.
- **macOS mic permission:** `build-macos.sh` must keep `NSMicrophoneUsageDescription` in Info.plist and ad-hoc sign the bundle — without it macOS never prompts and input is pure silence. `MicTest::blocked()` detects all-zero input and Settings → Voice shows the fix
- **macOS:** Requires `-ObjC` linker flag for libwebrtc Objective-C categories (`.cargo/config.toml`).
- **TLS:** `livekit` crate requires `native-tls` feature for WSS connections.

## Performance Notes
- Member list lazy-loads: 30 initially, more on scroll. Avatars resolved in background batch.
- Animations (`anim.rs`): `iced_gif::Frames` decodes every frame to full-canvas RGBA up front, so `anim::decode` reads the decoded size from the GIF headers first (frames counted via `next_frame_info`, no pixels decoded) and refuses anything over `ANIMATION_MAX_BYTES` (128 MB) — a few-KB GIF can declare gigabytes; animated WebPs are checked before transcoding. `FramesCache` evicts oldest-first by decoded bytes (`FRAMES_CACHE_BYTES` 512 MB, GIF search previews `PREVIEW_CACHE_BYTES`)
- Shared statics / caches lock with `.lock().unwrap_or_else(|e| e.into_inner())` — never `.unwrap()`, which turns one panic into a crash on every later access
- Media caches: SQLite `media_cache` pruned at login (`prune_media_cache`) to `MEDIA_DB_CACHE_LIMIT` (1500) entries and `MEDIA_DB_CACHE_BYTES` (300 MB), newest by the indexed `stamp` column (rowids aren't stable across VACUUM); entries over `MAX_CACHED_ENTRY_BYTES` (12 MB, i.e. videos) aren't stored. Entries are encrypted bytes (`cache_media(key, &[u8])` / `get_cached_media -> Vec<u8>`, see Local data at rest). VACUUM only when >25% of pages are free. `cache_media` is INSERT OR REPLACE. Data dir is chmod 0700 on unix.
- Inline image / video downloads share one `MEDIA_FETCHES` semaphore (`MEDIA_FETCH_CONCURRENCY` 4; cache hits skip it): unthrottled, a fresh install's first room/thread opened every download at once and everything — thread `/relations`, receipts, media — hit the SDK's 30 s timeout together. The plain-mxc fallback (when fetching the event fails) rejects anything that doesn't look like an image (`looks_like_image`) — in an encrypted room it's ciphertext, which was cached. Failures go to `image_failed` (`ImageFailed`) and retry after `IMAGE_RETRY_AFTER`. Watcher backfill retries a failed page `MAX_BACKFILL_RETRIES` times with doubling backoff instead of leaving the view empty
- Avatar cache stores `image::Handle` (cheap Arc clone) to avoid re-decoding on every render.
- Inline image cache persisted to SQLite (base64) for instant display on restart. Cache reads, base64 and writes run in the image task (`read_cached_image`, `spawn_blocking`), never on the UI thread; both cache hits and downloads arrive as `ImageResolved`, which only builds handles (animated frames via `gif_frames_task`). Video thumbnails likewise (GStreamer in `spawn_blocking`).
- syntect `SyntaxSet`/`ThemeSet` loaded once via `LazyLock` statics.
- SDK timeline output used directly — no client-side message merge. Edits applied by SDK. Parsed message bodies (HTML → spans, syntect) memoized in `html::BodyCache`; cleared on theme change or room-name changes.
- Empty messages filtered at load time, not per-render. New message detection via timestamp tracking.
- Thread counts computed at update time, not per-render.

## Update check (desktop)
- `core::release` is the desktop's self-discovery of updates (the Android `Update.kt` port): at startup `new_with_init` fetches `api.github.com/repos/phrac/fluxchat/releases/latest`, compares `tag_name` to `CARGO_PKG_VERSION` with the same part-by-part rule as Android (`is_newer`), and `Message::UpdateChecked` arms `FluxChat::update_available` → a yellow status-bar chip "Update available (vX.Y.Z)" that opens the release page via `OpenUrl` (no self-update installer — the release page is the whole upgrade path, honest for unsigned macOS builds). Once a day: the attempt is stamped in settings `update_last_check` *before* the fetch, so failures rate-limit too; every failure path is a `tracing::warn!` and no UI. The repo is private today, so the unauthenticated endpoint 404s and the chip can't fire until it goes public (same caveat as the phone). `FLUXCHAT_RELEASES_URL` points the check at a stand-in (that's how the chip was screenshotted against the private repo; the chip target stays the real GitHub page). `crates/app` carries the real version (0.2.2) so the comparison means something; `build-macos.sh` copies it into Info.plist.
